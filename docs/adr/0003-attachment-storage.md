# ADR-0003. Где хранить пользовательские вложения

- Статус: принято
- Дата: 2026-11-23

## Контекст

В ЛР2 приложение TimeCapsule (PHP + PostgreSQL 16) хранило пользовательские вложения на локальном диске сервера приложения в директории `storage/uploads`.

После разделения инфраструктуры в ЛР3 приложение и база данных работают на отдельных EC2-инстансах внутри VPC `timecapsule-dev-vpc`.

Однако вложения по-прежнему привязаны к диску `app-server`. Если пересоздать сервер приложения, можно потерять доступ к пользовательским файлам. Если запустить второй экземпляр приложения за балансировщиком нагрузки, он не будет видеть файлы, загруженные на первый сервер.

Нужно выбрать место для хранения вложений, которое не зависит от конкретного EC2-инстанса. Условия такие:

- проект учебный, поэтому постоянные дополнительные расходы нужно минимизировать;
- файлы должны сохраняться при замене или отказе сервера приложения;
- в дальнейшем приложение должно поддерживать несколько экземпляров за балансировщиком нагрузки;
- доступ к вложениям должен оставаться закрытым для посторонних;
- пользователь должен получать файл напрямую из хранилища, не заставляя сервер приложения передавать его содержимое.

## Решение

Переносим пользовательские вложения в **Amazon S3**.

Для этого создан бакет `timecapsule-dev-uploads-coffee` в регионе `us-east-1`. Все вложения приложения сохраняются под префиксом `uploads/`.

Бакет закрыт для публичного доступа, использует шифрование SSE-S3 и версионирование. Политика бакета запрещает HTTP-запросы, разрешая доступ только по HTTPS.

Для приложения создана IAM-политика `timecapsule-dev-app-s3`, которая разрешает читать, загружать и удалять объекты только внутри `uploads/`. Приложение получает эти права через IAM-роль `timecapsule-dev-app-role`, привязанную к EC2 `app-server`. Постоянные ключи доступа AWS в `.env` не хранятся.

Модуль хранения приложения переписан с использованием AWS SDK for PHP. При скачивании вложения приложение проверяет права пользователя на капсулу, создаёт подписанный URL сроком на 5 минут и перенаправляет браузер на S3. Сам файл передаётся непосредственно из S3, минуя сервер приложения.

## Рассмотренные альтернативы

- **EBS — отдельный диск сервера приложения.** Самый простой вариант: подключить дополнительный том к `app-server` и продолжить работать с файлами через обычную файловую систему. Данные можно сохранить при удалении EC2, если не удалять сам том, а для резервного копирования использовать Snapshots.
  Минусы: EBS привязан к зоне доступности, и обычный том нельзя просто использовать как общую файловую систему с нескольких серверов. При появлении нескольких экземпляров приложения потребуется отдельно решать синхронизацию и доступ к файлам. При замене сервера необходимо переподключать том или восстанавливать его из снимка.

- **Amazon EFS — общая файловая система.** Несколько EC2 могут одновременно работать с одними файлами через общую файловую систему. Она хорошо подходит для ситуации, когда несколько серверов должны использовать одинаковую структуру директорий без изменения существующего кода хранения.
  Минусы: необходимо дополнительно настраивать файловую систему, точки монтирования и сетевой доступ. Для небольшого учебного проекта это избыточное решение, а постоянное использование EFS создаёт дополнительные расходы.

- **Amazon S3 — объектное хранилище (выбрано).** Файлы хранятся отдельно от EC2 и доступны через API. Несколько серверов могут обращаться к одному бакету, а браузер может скачивать вложения напрямую по подписанному URL.
  Минусы: нельзя работать с объектами как с обычными файлами через `fopen()` или стандартные операции файловой системы. Необходимо использовать AWS SDK и управлять доступом через IAM. Также оплачиваются хранение, запросы и передача данных.

## Последствия

- **Плюс: файлы больше не зависят от сервера.** При замене `app-server` не нужно переносить пользовательские вложения. Достаточно развернуть приложение на новом EC2 и привязать к нему IAM-роль `timecapsule-dev-app-role`.

- **Плюс: браузер получает файлы напрямую из S3.** Сначала приложение проверяет, имеет ли пользователь право открыть капсулу. Затем формируется подписанный URL, и браузер загружает файл непосредственно из бакета. Срок действия ссылки составляет 5 минут. После истечения этого срока ссылка перестаёт работать. Она также не может действовать дольше временных учётных данных IAM-роли, которыми была подписана. Пользователь может переслать ссылку другому человеку, поэтому доступ к ней фактически получает любой, кто ею располагает, пока она действительна.

- **Защита от случайного удаления.** В бакете включено версионирование. При обычном удалении S3 создаёт Delete Marker, а предыдущие версии сохраняются и могут быть восстановлены. IAM-политика приложения не содержит `s3:DeleteObjectVersion`, поэтому даже при получении доступа к серверу злоумышленник через роль приложения не сможет физически удалить историю версий.

- **Ограничение стоимости хранения.** Создано правило жизненного цикла `timecapsule-dev-noncurrent`: неактуальные версии переходят в Standard-IA через 30 дней и удаляются через 90 дней, кроме двух самых новых неактуальных версий. Незавершённые multipart-загрузки удаляются через 7 дней. Это позволяет ограничивать рост хранилища. При этом удаление старых версий означает, что восстановить их после окончания срока хранения уже не получится.

- **Когда появятся несколько серверов приложения.** Все экземпляры будут использовать один и тот же бакет S3. Балансировщик нагрузки сможет направлять запросы на любой сервер, поскольку вложения не хранятся локально. Не понадобится синхронизация файлов между EC2. Для этого каждому серверу потребуется соответствующая IAM-роль.

- **Переход к приватным подсетям.** Когда перед приложением появится ALB, пользователи будут обращаться к DNS-имени балансировщика, а не к IP конкретного EC2. Публичный IP приложения станет не нужен, а серверы можно будет переместить в приватные подсети. Для доступа к S3 из них можно настроить Gateway VPC Endpoint, чтобы не держать NAT Gateway только ради обращений к S3.

- **Минус: приложение стало зависеть от доступности AWS S3 и сетевого подключения к нему.** При недоступности S3 операции с вложениями не будут работать, даже если сам сервер приложения и база данных доступны. Кроме того, добавилась зависимость от AWS SDK и правильной настройки IAM.
